# LLM 智能体的外化架构：记忆、技能、协议与工程框架

> **作者**：李玮宣
> **日期**：2026-05-11

## 技术背景

### 从人类认知外化到机器智能外化

人类文明史本质上是一部认知外化史：口语将私人思想转化为可共享的符号形式，文字将知识从脆弱的生物记忆迁移到持久的物质记录，印刷术将知识复制机械化并推向社会规模，数字计算则将算术与符号操作从神经劳动转移到可编程机器。贯穿这些变迁的关键变化，并非人类在失去外部工具后变得更弱，而是外部工具通过将选定的认知负担向外转移，释放了有限的内部资源，用于规划、抽象与创造。

如今，这一外化模式在机器智能的前沿——大语言模型（LLM）智能体的设计中再次重现。本文解读的综述论文《Externalization in LLM Agents: A Unified Review of Memory, Skills, Protocols and Harness Engineering》（2026年4月）正是在这一视角下，系统性地审视了 LLM 智能体的核心设计选择。

### 从 Weights 到 Context 再到 Harness：能力的渐进外化

LLM 智能体的近期历史可被理解为一种从模型自身向外逐步迁移的过程。能力首先被视为**权重**的属性，然后被视为**提示词和上下文窗口**的属性，如今则越来越多地被视为模型运行于其中的**基础设施**的属性。

**第一阶段：能力在权重中（Capability in Weights）**。在最早期的 LLM 部署浪潮中，能力几乎完全被等同于模型参数。预训练将统计规律、世界知识和潜在推理习惯压缩进权重，缩放定律揭示了参数量与性能之间的可预测关系。GPT-4、Gemini、DeepSeek-V3 等系统展示了大规模多任务能力，领域内的主流叙事将更强的智能体等同于更大、更好训练的模型。然而，权重空间编码将知识、过程与策略过于紧密地耦合到一个静态产物中，更新单个事实就需要重新训练或知识编辑，审计行为原因也异常困难。

**第二阶段：能力在上下文中（Capability in Context）**。注意力从模型修改转向输入设计。提示工程（Prompt Engineering）、思维链（Chain-of-Thought）、ReAct、检索增强生成（RAG）等技术表明，模型行为可以在不触及权重的情况下被大幅改变。上下文成为开发者"为模型呈现认知"的媒介。但上下文窗口是有限的、昂贵且嘈杂的，"迷失在中间"现象表明长输入中模型注意力不均匀，并且上下文是短暂的——除非状态被外化到别处，否则每个新会话都始于部分失忆。

**第三阶段：能力在基础设施中（Capability through Infrastructure）**。当前的 Harness 阶段代表了能力超越提示管理、扩展到持久基础设施的阶段。Auto-GPT、BabyAGI 等最早将 LLM 包裹在任务队列、持久记忆和 Web 访问的循环中。随后 AutoGen、MetaGPT、CAMEL 等框架进一步将控制流、环境访问和重用显式化。在编码、研究、企业等部署领域，可靠性越来越依赖于外部记忆存储、工具注册表、协议定义、沙箱、可观测性管道和审批回路。

![三层能力演进](attachments/111014a3a2aab424326d49d4941936a1172a2d1b198f7d26bfd2e6203549f73c.jpg)

*图：社区主题在三个能力层间的演变。Weights、Context、Harness 三层展示了 LLM 智能体社区的重心如何随时间向外移动——从参数化知识和提示工程，转向工具生态、协议、技能和多智能体编排等 Harness 层基础设施。*

### 核心主张：外化作为统一逻辑

论文的核心主张是：**外化（Externalization）**——将认知负担从模型内部计算逐步迁移到持久、可检查、可重用的外部结构——是统一了记忆、技能、协议和工程框架（Harness）等近期进展的**转换逻辑**。这不只是工程便利性的论述，而是关于可靠智能体能力从何而来的论断：它并非仅来自越来越大的模型，而是来自系统性地重构任务需求，使内部能力与外部基础设施共同覆盖所需的全方位能力。

一个具体的例子能帮助理解：考虑一个被要求实现代码特性、运行测试并提交 PR 的软件工程智能体。在没有外化的情况下，模型必须在脆弱的提示中保持仓库结构、项目惯例、工作流状态和工具交互。有了外化，持久化的项目记忆提供上下文，可重用的技能文档编码惯例和工作流，协议化的工具接口强制执行正确的模式，工程框架则对步骤进行排序、验证输出并管理失败。基础模型可能完全不变，变化的是它被要求解决的任务的**表示形式**。

## 技术方案

本篇综述将 LLM 智能体的外化架构归纳为三个核心外化维度（记忆、技能、协议）和一个统一的工程层（Harness）。下面逐一展开它们的构成与技术方案。

### 一、外化状态：记忆系统（Memory）

记忆外化解决的是智能体的**时间连续性负担**。裸语言模型必须在短暂的提示中承载连续性、先前经验、用户特定事实和未完成的工作。一旦任务跨越多个会话、分支或中断，这种负担就变得既不稳定又昂贵。记忆将其外化为可被写入、更新和检索的持久状态。

![记忆外化架构](attachments/bf78a2401063df7c1e2fee9564bfa901d5e68c753c8840f5021af845d8720fa0.jpg)

*图：记忆作为外化状态。原始上下文和反馈被转化为四类持久记忆维度——工作上下文、情景经验、语义知识和个性化记忆——并通过逐步更受管理的架构进行组织。*

#### 1.1 记忆的四重维度

记忆外化不是单一的同类数据库，而是跨越多个抽象层级的时间连续性负担：

- **工作上下文（Working Context）**：当前任务的实时中间状态——打开的文件、临时变量、活跃假设、部分计划和执行检查点。它变化快速，过期即失效。例如 OpenHands 等编码智能体通过将草稿、终端状态和工作区产物外化到提示之外，使智能体可以从当前操作状态恢复执行，而不是从零重建。
- **情景经验（Episodic Experience）**：记录之前运行中发生的事——决策点、工具调用、失败、结果和反思。其价值不仅在于存档，检索到的事件可作为具体先例，帮助避免重复已知错误。例如 Reflexion 将失败尝试的反思摘要存储为可重用经验；AriGraph 将不熟悉环境中的局部交互轨迹构建为情景记忆，从中推导更广泛的世界模型。
- **语义知识（Semantic Knowledge）**：存储超越任何单一事件的抽象——领域事实、通用启发式、项目惯例和稳定的世界知识。它与情景记忆的功能区别在于：情景记忆说某个案例中发生了什么，语义记忆说什么在多个案例中倾向于成立。当前的知识库与 RAG 语料库是最常见的外化语义记忆形式。
- **个性化记忆（Personalized Memory）**：跟踪特定用户、团队或环境的稳定信息——偏好、习惯、重复约束和先前交互。这部分状态不应与智能体的通用自我改进存储混在一起，因为用户特定痕迹遵循不同的保留、检索和隐私规则。例如 IFRAgent 从移动环境的演示中构建用户习惯仓库，VARS 将跨会话偏好卡片存储在隔离的用户记忆空间中。

#### 1.2 记忆架构的四个范式

按照存储与推理的分离程度，当前系统可分为四种架构范式：

| 架构 | 核心思想 | 代表工作 | 局限性 |
|------|---------|---------|--------|
| **单体上下文（Monolithic Context）** | 所有历史或摘要直接保留在提示中 | 早期系统 | 容量差、摘要漂移、会话后状态消失 |
| **上下文+检索存储（Context with Retrieval Storage）** | 仅保留近期工作状态在上下文中，长期存储在外并按需检索 | 生产级助手、编码智能体 | 将记忆质量变成检索问题；错误记录可能分散注意力，正确记录可能被遗漏 |
| **层次化记忆与编排（Hierarchical Memory）** | 引入显式的提取、整合和遗忘操作，将记忆变为有管理的生命周期 | Mem0, Memory-R1, MemGPT, MemoryOS, Memory Bank, MIRIX, xMemory | 依赖人工设计的启发式规则 |
| **自适应记忆系统（Adaptive Memory）** | 模块、路由决策或检索策略根据经验自我调整 | MemEvolve, MemVerse, MemRL, MOE 路由 | 仍在发展，需要更成熟的评估体系 |

关键的技术方案包括：
- **MemGPT / MemoryOS**：借鉴操作系统逻辑，将热工作状态与冷长期存储分离，按任务需求跨层交换信息，在固定上下文预算下提升有效容量
- **GraphRAG**：引入图结构和社区级检索，捕获超越简单关键词匹配的关联性
- **ENGRAM**：将记忆压缩为潜在状态表示
- **SYNAPSE**：使用扩散激活在统一的"情景-语义"图上恢复非局部的相关性

#### 1.3 记忆作为认知产物

论文从 Norman 的认知产物理论出发，指出记忆外化实现的**表征转换**是：将一个内部回忆问题转变为外部识别与检索问题。模型不再需要从参数中恢复相关历史，而是需要识别和使用记忆系统已经浮出的经过筛选的历史切片。成功的标准不是"我们存了多少"，而是"我们是否使当前决策变得可读"。

### 二、外化专业知识：技能系统（Skills）

技能外化解决的是智能体的**过程性负担**。语言模型虽然原则上知道如何解决某类任务，但可靠执行仍需要每次重新构建工作流、默认值和约束。这种负担随着任务长度、环境特异性和分支决策数量的增加而增长，体现为**方差**：遗漏步骤、不稳定的工具使用和不一致的停止条件。

![技能外化架构](attachments/20cd492f7183d043d3d67741d243ce481a54013b3ad8db6f05a2e1a528b92441.jpg)

*图：技能作为外化专业知识。展示了技能从调用、选择到执行的完整生命周期——包括技能获取的四种路径，技能产物的三种组成，以及激活管道中的渐进披露机制。*

#### 2.1 技能的三个组件

技能外化关注的是**过程性专业知识**，而非孤立的动作接口。这种专业知识有三个耦合组件：

- **操作流程（Operational Procedure）**：任务骨架——将复杂任务分解为步骤、阶段、依赖关系和停止条件。它解决的核心问题是：LLM 智能体的许多错误并非来自动作层面的无能，而是来自过程层面的不稳定（跳过步骤、错序操作、提前终止）。外部化过程将这些脆弱的过程知识转化为显式的操作路径。
- **决策启发式（Decision Heuristics）**：如果说流程定义了执行的骨架，启发式则管理分支处发生什么。真实任务很少以固定管道展开——工具会失败、观测有噪声、多个局部可行的动作可能竞争。外化这些启发式改变了推理努力的分布，将"先试什么、何时回退、什么证据足够、哪些权衡优先"等经验法则编码为可重用的规则。
- **规范性约束（Normative Constraints）**：过程在什么条件下算作可接受。一个工作流可能技术上有效，但仍然是违规、不安全或操作不当的。在真实部署中，执行受测试要求、范围限制、访问限制、可追溯性期望和领域特定操作规则的约束。一旦外化，这些约束就不再仅仅是事后评估标准，而是成为技能本身的一部分。

#### 2.2 技能的运行生命周期

在成熟的智能体系统中，技能外化不限于写下指令，而是一个完整的运行时过程：

1. **规范（Specification）**：技能始于声明性规范——SKILL.md、指令文件或清单。它们描述技能做什么、适用于什么场景、依赖什么、必须满足什么约束。良好形成的技能规范应覆盖五类信息：能力边界、适用范围、前置条件、执行约束，以及示例和反例。

2. **发现（Discovery）**：一旦技能成为显式产物，就需要注册和发现机制。智能体不能不加区分地为每个任务加载每个可用技能。发现过程依赖语义检索、结构化元数据或任务分解，且必须考虑不仅主题相似性，还包括任务复杂性、环境假设、操作约束和风险条件。

3. **渐进披露（Progressive Disclosure）**：发现一个技能不等于将其全部内容立即注入活跃上下文。因为长上下文并不等于更好的性能，当前技能系统采用渐进披露策略——先暴露技能名称和简要描述（最小层级），更深层级展示适用条件、必要前置和主要约束，仅在最深层级才加载完整指南。Claude Code 的技能系统是这一模式的典型代表。

4. **执行绑定（Execution Binding）**：技能只是认知层面的描述，需通过绑定过程转化为当前环境中的具体操作。技能指定"智能体应该搜索相关代码、运行测试、总结 diff"，但具体操作由搜索工具、文件操作、Shell 命令和测试运行器执行。工具提供可执行的操作，协议管理操作的描述和调用方式，技能则提供如何将它们组合成可重复任务的高级策略。

5. **组合（Composition）**：技能系统的价值在于技能可以被组合。常见组合模式包括串行执行、并行分工、条件路由和递归调用子技能。组合不仅是将多个过程片段拼接，而是对过程专业知识本身的高层重用。

#### 2.3 技能获取的四种途径

技能获取是一个进化过程，过程性知识通过四种途径进入系统：

- **人工编写（Authored）**：最常见且稳定的途径。SKILL.md、AGENTS.md、组织 SOP 模板都是人工设计的过程性能力包。当智能体在部署中反复表现出失败模式时，工程师可以更新相应技能，将观察到的失败转化为明确的过程或约束。
- **轨迹蒸馏（Distilled）**：从历史轨迹、实践痕迹或其他存储经验中归纳技能。当某些成功结构在任务间重复出现时，系统可以将这些模式抽象为更稳定的过程单元。例如 Skill Set Optimization 从有奖励的子轨迹中提取可迁移技能；MemSkill 进一步表明某些记忆操作本身可以被重新表述为可学习的技能。
- **环境发现（Discovered）**：智能体通过环境交互自主发现新技能。Voyager 在 Minecraft 场景中展示了这一范式——探索、执行反馈、自我验证和课程驱动任务选择共同产生一个持续增长的技能库。PolySkill 进一步将抽象目标与具体实现分离以改进技能重用。
- **组合形成（Composed）**：许多高层能力并非从零发明，而是从已有底层或中层技能组装而成。一旦某个已有技能的特定组合被反复验证有效，该组合本身可以被打包为新的更高层技能。

### 三、外化交互：协议系统（Protocols）

协议外化解决的是智能体的**交互负担**。裸模型可能推断某个工具应该被调用、子智能体应该被委派、响应应该展示给用户，但如果没有显式契约，它还必须即兴构建消息格式、参数结构、生命周期语义、权限和恢复行为。这种负担将每次外部行动变成脆弱的提示跟随练习。

![协议外化架构](attachments/a5b4994be1a348dd7e49e4162cd6e9bd5f8147445b699aaaa3061ecbcc00a43b.jpg)

*图：协议作为外化交互。上图：智能体交互的演化轨迹——从孤立模型调用、硬编码 API 连接到标准化协议，最终走向去中心化的智能体网络。下图：工程框架通过 INTERACT、PERCEIVE、COLLABORATE 三个功能面实现外化交互管理。*

#### 3.1 协议外化的四个维度

协议将交互中原本需要模型推断的负荷，转化为显式的、机器可读的契约：

- **调用语法（Invocation Grammar）**：每个工具调用、API 请求或委派消息都需要格式——参数名、类型、顺序和返回结构。协议将其外化为模式和类型接口，让模型填充字段而非猜测语法。
- **生命周期语义（Lifecycle Semantics）**：多步交互需要协调——谁下一步行动、什么状态转换被允许、任务何时完成或失败。协议将这些顺序规则外化为显式的状态机或事件流。
- **权限与信任边界（Permission & Trust Boundaries）**：真实世界的智能体行动受授权范围、数据流向和证据要求的限制。协议将这些约束外化为运行时可以执行的、可检查的规则。
- **发现元数据（Discovery Metadata）**：在智能体与工具或另一智能体交互之前，它必须知道哪些能力可用以及如何获取。协议将此发现问题外化为注册表、能力卡片和模式端点。

#### 3.2 协议族系与代表方案

按交互对象划分，当前主流协议可分为四个族系：

**Agent-Tool 协议族**：最早成熟的协议族。MCP（Model Context Protocol，Anthropic 提出）是最清晰的代表——它为智能体提供了跨异构服务发现工具、检查其模式和调用它们的标准化方式。架构上，MCP 通过 JSON-RPC 2.0 将工具访问转变为基于协议的集成，实现动态能力发现、标准化访问、结构化请求/响应交换和模块化扩展性。ToolUniverse 进一步扩展了专用工具模式和交互惯例。

**Agent-Agent 协议族**：当多个智能体协作时，交互本身成为系统问题。A2A（Google 提出）是最突出的当前例子——通过 Agent Cards 等产物标准化能力发现，支持异构智能体之间的任务导向通信、状态更新、协商和流式进度跟踪。ACP（IBM 提出）强调通过熟悉的 REST/HTTP 模式实现轻量级采用。ANP 则向开放、互联网规模的互操作性推进，支持去中心化身份、跨域发现和端到端安全通信。

**Agent-User 协议族**：形式化智能体运行时与面向用户系统之间的边界。A2UI（Google 提出）代表界面生成分支——让智能体以受限的声明式格式描述 UI 结构，宿主应用可跨平台安全渲染。AG-UI（CopilotKit 提出）代表流式状态分支——标准化类型化的执行事件（运行开始、文本输出、工具调用参数/结果、完成、错误），前端可订阅事件流并渲染运行时状态。

**领域专属协议**：针对高风险垂直工作流。UCP（Google 提出）用于智能体商务，标准化目录、请求和结账流程；AP2（Google Cloud 提出）用于支付，强调授权、签名、可审计性和带有证据的交易对象。

#### 3.3 协议在工程框架中的运行

协议在工程框架中通过三个功能面运行：

1. **意图捕获与规范化**：将模型产生的语言转化为运行时可以验证和执行的显式命令或事件。自由文本提议被映射到协议对象，根据当前上下文和权限边界检查，不符合契约的则拒绝或修正。
2. **能力发现与工具描述**：在会话开始或阶段转换时，运行时通过标准化消息暴露当前可用工具、其模式和输入/输出结构。这降低了上下文膨胀并让能力边界变得可治理。
3. **会话与生命周期管理**：运行时在多个轮次、上下文窗口和执行阶段间保留交互状态——标识符、角色、待处理动作、阶段转换和允许的下一步动作。

### 四、统一外化：工程框架（Harness Engineering）

如果说记忆、技能和协议分别外化了时间状态、过程专业知识和交互结构，那么工程框架（Harness）则是**将这些外化模块组合成连贯智能体的运行时环境**。它不是一个与三者并列的第四类外化维度，而是包含并协调三者运行的认知环境。

![工程框架架构](attachments/f65dc753c6a1b05f7d651af26b17ec462839016233438d22fa329107a7d03c07.jpg)

*图：工程框架作为认知环境。基础模型（智能体核心）位于中心，六个工程框架维度形成协调环——三个外化模块（Memory, Skills, Protocols）提供外化的认知内容，三个操作面（Permission, Control, Observability）治理这些内容在运行时的访问、约束和监控。*

#### 4.1 工程框架的六个设计维度

工程框架的设计可沿六个分析维度进行拆解，每个维度解决外化模块如何被组合成可运行智能体的一个方面：

**① 智能体循环与控制流（Agent Loop & Control Flow）**

感知-检索-规划-行动-观测循环是工程框架的时间骨干。实用系统在循环结构上有显著变化：单循环设计将推理和行动交错在一次生成中；层次化设计分离出分解目标的规划智能体和执行各步骤的执行智能体；多智能体设计将子任务路由到具有不同工具集和权限范围的专门智能体。工程框架在此基础上增加了**终止控制**——最大步数限制、递归深度界限、每步成本上限和超时约束——这些不是次要的安全措施，而是定义智能体执行包络的核心控制。

**② 沙箱与执行隔离（Sandboxing & Execution Isolation）**

当智能体在世界上行动——写文件、执行 Shell 命令、调用外部 API——工程框架必须决定暴露多少环境以及如何容纳非预期的副作用。Codex 风格智能体为每个任务在专用云沙箱中运行，配备独立的文件系统快照、网络限制和资源配额。Claude Code 采用互补方法——暴露渐进式权限模式（从完全自主执行到每个工具调用都需用户批准）。沙箱不仅是安全围栏，更是**认知边界**——通过移除不相关状态和限制危险行动来简化智能体的操作环境。

**③ 人类监督与审批关卡（Human Oversight & Approval Gates）**

完全自主很少适用于部署的智能体。三种常见模式：**执行前批准**——在每次可能有后果的行动前暂停并要求确认；**执行后审查**——让智能体行动，但在提交或继续前展示结果供检查；**升级触发**——让智能体在正常条件下自主运行，但当特定风险信号被检测到时停止并请求人类输入。Hook 系统通过允许操作员将任意验证逻辑附加到智能体循环中的特定生命周期事件来泛化这些模式。自主级别因此不是智能体的二元属性，而是工程框架的可配置参数。

**④ 可观测性与结构化反馈（Observability & Structured Feedback）**

不留下可检查痕迹行动的智能体是不可调试、不可审计和不可改进的。可观测性在实现层面包括：每次模型调用、工具操作、记忆读写的结构化日志；将每次行动链接到其因果前件的执行轨迹；以及步数、token 消耗、错误率和延迟等聚合指标。这些记录服务于两个目的：外部支持调试、合规审计和事故后分析；内部则闭合了连接执行结果与产生它们的模块的反馈回路——失败的工具调用可以触发记忆写入，重复失败的模块可以标记技能进行修订。

**⑤ 配置、权限与策略编码（Configuration, Permissions & Policy Encoding）**

工程框架必须编码的不仅是智能体可以做什么，还有它在什么条件下被允许做什么。配置通常跨多个范围分层：用户级设置编码个人偏好和信任边界；项目级设置指定哪些工具可用、哪些文件路径可访问、哪些命令需要批准；组织级设置施加合规约束、成本上限和数据处理规则。这种分层模型意味着同一基础智能体可以根据部署上下文在不同策略制度下运行，而无需更改模型或加载的技能产物。

**⑥ 上下文预算管理（Context Budget Management）**

上下文窗口是任何智能体系统中最稀缺的共享资源。记忆检索、技能加载、协议模式、工具描述和模型自身的推理轨迹都在竞争同一有限 token 预算。有效的上下文管理通常结合三种策略：**摘要压缩**——将较早的对话轮次和执行历史压缩为更短的表示，保留决策相关信息；**优先级淘汰**——降级或移除与当前子任务相关性已衰减的上下文条目；**分阶段加载**——确保详细的过程指南仅在匹配的任务模式被检测到时才进入上下文。工程框架联合编排这些策略，因为最佳分配取决于当前执行阶段。

#### 4.2 四大模块的交叉耦合

记忆、技能、协议和工程框架并非孤立运作。论文识别了六条系统级交互流：

![模块耦合图](attachments/7fc09fdf4bf9fe7712078db0a6b8e99f3d0e4bbd507f9e14c0d148507fdae456.jpg)

*图：记忆、技能和协议之间的耦合关系。六条箭头总结了三者在工程框架内如何相互增强。*

- **记忆 → 技能（经验蒸馏）**：重复的轨迹可被蒸馏为可重用过程，是累积经验变为编撰专业知识的主要路径
- **技能 → 记忆（执行记录）**：每次技能执行产生痕迹和失败，被捕获为持久证据以供验证和修订
- **技能 → 协议（能力调用）**：技能通过协议跨越从抽象过程到受治理行动的边界
- **协议 → 技能（能力生成）**：一旦接口标准化，编码接口特定最佳实践变得更容易，催生新技能
- **记忆 → 协议（策略选择）**：存储的上下文影响协议路径选择——历史成功率、用户偏好决定请求是本地处理还是委派
- **协议 → 记忆（结果同化）**：每次协议交互产生必须被保留的状态——工具输出、审批事件、错误负载

这些模块还竞争同一稀缺资源（上下文窗口），且交互发生在不同时间尺度上（协议交互是同步和快速的，技能加载发生在任务边界，记忆蒸馏和技能演化跨越多个会话）。

#### 4.3 参数化能力 vs. 外化能力：权衡空间

论文最终将设计问题定位于一个系统分区问题：哪些负担应该留在参数中，哪些应该被外化？四个维度框定了这一决策：

| 维度 | 偏向参数化 | 偏向外化 |
|------|-----------|---------|
| **更新频率** | 稳定的背景能力（语言理解、常识推理） | 快速变化的知识（API、组织结构、实时环境状态） |
| **可重用性** | 一次性或高度特异化的行为 | 跨任务、用户、智能体反复需要的能力 |
| **可审计性与治理** | 概率性行为塑造（RLHF） | 确定性约束强制执行（模式验证、断路器、可追溯执行记录） |
| **延迟与简单性** | 超快、低方差、纯语义任务 | 需要持久化、复用和显式控制的场景 |

最优分区不是静态的——随着模型能力增强和外部基础设施成熟，边界将持续移动。

## 技术总结

本文解读的综述论文提出了一种系统级的视角，将 LLM 智能体领域的诸多进展统一在**"外化"**这一核心概念之下。论文的核心贡献在于建立了以下架构框架：

**三个外化维度解决了智能体的三种根本性不匹配**：
- **记忆（Memory）** 将时间连续性从脆弱的上下文窗口转移到持久、可搜索的存储中，完成"从回忆到检索"的表征转换
- **技能（Skills）** 将过程性专业知识从反复即兴生成转换为可发现、可加载、可组合的显式产物，完成"从生成到组合"的表征转换
- **协议（Protocols）** 将交互协调从临时提示约定转换为机器可读、可治理的显式契约，完成"从临时到结构化"的表征转换

**工程框架（Harness）** 是协调这三个维度的运行时环境，通过六个设计维度（循环控制、沙箱、人类监督、可观测性、配置管理和上下文预算）将外部化模块组合成可靠的智能体行为。

论文的深层洞见在于：**外化的价值不在于简单地"添加更多组件"，而在于它改变了模型被要求解决的任务的表示形式**。这与 Norman 的认知产物理论和 Kirsh 的互补策略理论一脉相承——智能体的可靠能力不仅来自于更强的模型，更来自于更好地组织记忆、更精确地约束执行、更清晰的反馈通道和更精心设计的执行环境。

对于工程实践而言，这意味着智能体设计的重心正在从"如何让模型更强"转向"如何构建更好的外部认知基础设施"——这不是对模型能力的否定，而是对能力边界的务实认知：将模型擅长的事留在内部，将需要持久化、可复用和可治理的事交给外部。

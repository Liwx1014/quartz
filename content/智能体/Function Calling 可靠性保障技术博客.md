# 一个模糊的系统，如何产出精确的结果？—— Function Calling 可靠性保障深度拆解

> **作者**：Lwx
> **日期**：2026-05-11

## 技术背景

想象这样一个场景：你让一个只会说"差不多"的助手去银行转一笔账。你跟它说"给张三转一万块"，它有时候能准确执行，有时候却把收款人填成"张先生"、把金额写成"10000元"（而不是 `10000`），甚至偶尔干脆忘了转账这事，开始跟你聊天气。更头疼的是，你无法预测它什么时候会出错——同样的指令，上一秒还好好的，下一秒就崩了。

这就是 Function Calling 在生产环境中面临的真实困境。LLM 本质是一个基于概率采样的文本生成模型，它的强项是"说得像那么回事"，而不是"做得分毫不差"。当我们需要它生成一段推荐语、一篇总结时，措辞上的微小偏差无伤大雅；但一旦让它去调数据库、发 API、操作账户，任何微小的参数错误——多一个空格、少一个引号、枚举值拼错了——都会让下游系统直接拒绝执行，整个 Agent 流程戛然而止。

更棘手的是，这个问题很难通过"升级模型版本"或"把 Prompt 写得更长"来彻底解决。它根源上不是"模型不够聪明"，而是两种运行范式之间的结构性冲突：概率采样 vs. 确定性契约。要弥合这个裂缝，需要的不是某一层的极致优化，而是从请求进入模型到工具结果返回的全链路纵深防御。

## 技术方案

### 阶段一：意图理解 —— "你到底要不要调用工具？"

Function Calling 的可靠性风险，在用户输入到达的第一个瞬间就已经埋下了。模型必须先回答一个前置问题：**这条消息里，有没有隐含对一个外部工具的调用需求？**

这个问题分解成两个更细的决策："要不要调？"和"调哪个？"。两个都容易出错。

先说"要不要调"。用户说"帮我看看明天北京天气"，这显然需要调用天气 API；但用户说"今天天气真好啊"——这是闲聊还是触发查询？模型缺乏足够的上下文时，容易在两个方向上同时犯错：该调的时候不调（直接用自己的训练记忆编造一个"明天的天气"），不该调的时候乱调（把一句感叹误判为工具请求，浪费资源甚至产生副作用）。

再说"调哪个"。当一个 Agent 只有两三个工具时，选错概率较低；但当工具数量攀升到十几个甚至更多，模型面对的是一张越来越拥挤的"菜单"。`search_products` 和 `search_inventory` 都是搜索类工具，功能高度重叠，模型很难仅凭名称判定边界。在实际系统中，工具超过 10-15 个后选择准确率会出现明显拐点，这不是某个模型的问题，而是长上下文 + 相近语义双重压力下的必然结果。

**应对思路：用描述画边界，用分组缩范围。** 工具描述不能只是"查询产品信息"这样的技术注释，而要写成给模型的"使用说明书"——明确写出什么时候用它、什么时候不能用它、输入应该满足什么约束。同时，不要把所有工具一股脑塞进 Prompt。更务实的做法是动态注入：先根据用户意图做一轮粗筛，只把相关的 3-5 个工具放入当前上下文，把几十个工具的选择问题降维成小规模匹配问题。另外，在 System Prompt 中嵌入 2-3 个完整的调用示例（用户输入 → 工具选择 → 参数格式），能显著帮助模型建立"什么情况下调、什么情况下不调"的判断锚点。

### 阶段二：参数生成 —— "调哪个工具我选对了，但参数怎么写？"

工具选对只是第一步。更常见的失败发生在参数构造环节。模型正确选中了天气查询工具，但传了 `BJ` 而不是 `北京`，写了 `03/15/2024` 而不是 `2024-03-15`，或者干脆漏掉了 `unit` 这个必填字段。

这类问题的根源在于：模型是"看到过很多文本"而不是"理解类型系统"。它见过各种日期的写法，但不知道你的 API 只认 ISO 8601。它知道 `pending` 和 `Pending` 表示同一个意思，但不知道你的枚举校验是大小写敏感的。传统开发中靠编译器和类型系统就能拦住的错误，在 LLM 的 token 生成世界里，每一个都是潜在的炸弹。

**应对思路：用 JSON Schema 把边界写死，不要指望模型自觉。** 参数的定义不是"写完就行"——它的约束写得越细，模型的犯错空间越小。具体来说：能用 `enum` 就别只用 `string`（比如 `["celsius", "fahrenheit"]`），能用 `pattern` 就别只用 `type`（比如 `"^\\d{4}-\\d{2}-\\d{2}$"` 约束日期），能用 `minimum/maximum` 就别靠自然语言说"金额在 0 到 10000 之间"。这些约束有两个关键价值：一是给下游校验层提供自动化校验依据，二是模型在生成 token 时也会参考 Schema 中的约束信息做概率偏向。一个被 `enum` 锁死取值范围的字段，远比一个放飞的 `string` 型字段可靠。

### 阶段三：格式产出 —— "就算参数内容对了，你给的 JSON 能解析吗？"

参数语义对了，不代表产出物能被下游系统正确解析。在实际开发中，经常遇到模型输出的"JSON"外面多了一层 Markdown 代码块标记（```json ... ```），字段名多了个逗号，字符串少了引号——任何一个微小的语法瑕疵都会让 `JSON.parse()` 直接崩掉。

这类问题的解决思路，过去主要靠后处理——写正则、做容错解析、甚至让模型重新生成。但拼凑式的兜底始终不干净。真正从根本上解决问题的，是近年主流模型厂商力推的 **Structured Output（结构化输出）** 能力。

**Structured Output 的核心是受约束解码。** 普通模式下，模型生成每个 token 时，会从整个词表（几万个候选）中按概率采样。受约束解码的逻辑则完全不同：它根据你提供的 JSON Schema，**在每一步生成前动态计算当前语境下合法的 token 集合，把所有不合法的 token 概率直接置零**。比如模型刚生成 `{"city": `，Schema 定义了 `city` 必须是 string 类型——那接下来能生成的就只有引号开头的内容，数字 token、布尔 token 完全没有存在的可能。

这个机制从数学上保证了格式正确性——不是"尽量"，而是"一定"。但它有一个清晰的边界：**保格式，不保语义**。模型可能生成一个格式完美但值完全离谱的 JSON——比如把城市名填成了用户名——因为对模型来说，只要是合法字符串，受约束解码就不会拦截。格式保证是最后一公里的稳定器，但语义判断仍然需要其他层的协同。

### 阶段四：工程兜底 —— "外部世界不可控，你的系统扛得住吗？"

即使模型侧的输出完美无缺，真正的挑战才刚开始。外部 API 可能超时、限流、返回错误码，也可能返回一个完全出乎意料的数据结构。模型拿到工具返回结果后，还可能在解读时出错——把美元当人民币，从一堆字段里挑了错的那个。这些都不是模型的错，但你的系统必须能应对。

**参数校验层是工程侧的硬防线。** 最有效的实践是在模型输出工具调用指令和实际执行之间插入一个独立校验层。这个校验层不依赖模型判断——它用 jsonschema 库或 Pydantic 模型对参数做严格校验，检查类型、必填项、枚举合法性、数值范围。校验失败时，不是直接报错给用户，而是进入一个"带反馈的重试循环"：把具体的校验错误（比如 `"date 字段格式错误，期望 YYYY-MM-DD，实际收到 '03/15/2024'"`）作为上下文拼进下一轮 Prompt，让模型看到错误后重新生成。实测数据表明，这种带反馈的纠错循环可以修复约 80% 的参数级失败。

**重试策略需要区分失败原因，不能一刀切。** 参数校验失败走"带反馈重试"——模型需要看到出错信息来修正；外部 API 超时走指数退避重试——跟模型无关，是网络层面的容错；同一工具连续多次失败则触发降级——切到一个功能类似的备用工具，或者直接告知用户该操作暂不可用，而不是进入无限重试的死循环。Pydantic 在 Python 生态中已经成为 Function Calling 的标配方案：用 Pydantic 模型定义工具参数，自动产出 JSON Schema 给模型用，同时自动完成解析和校验，校验失败的 `ValidationError` 自带完整错误描述，可以直接反馈给模型。

### 阶段五：规模化带来的新挑战

当工具从两三个增长到几十个时，前面提到的所有问题都会被放大。更麻烦的是，还会涌现出单工具场景中不存在的新问题。

**工具混淆是第一大痛点。** 一组名字相近、功能重叠的工具（比如 `send_email` 和 `send_notification`）会让模型的选择边界变得模糊。逐一描述每个工具的用途还不够——需要**互相参照着写**，明确告诉模型："当场景 X 发生时用 A，当场景 Y 时用 B，你的判断标准是什么"。再配合工具分组——按业务域把工具分成若干组，模型先做粗粒度分组选择，再做细粒度工具选择——像两级菜单一样把选择空间降维。

**并行调用（Parallel Function Calling）引入依赖判断难题。** 现代模型支持在一次回复中同时触发多个工具，效率上去了，但也带来了"不该并行却并行了"的风险。比如要先查用户 ID 再下单的业务逻辑，模型可能误判为可并行操作，同时调用查询和下单，结果下单接口拿到的用户 ID 为空。工程上需要做执行层的依赖检查——检测到并行调用之间存在数据依赖时，自动转为串行。

**工具调用链需要模板约束。** 在复杂 Agent 中，一个用户请求可能触发 3-5 个工具串行调用，前一个工具的输出是后一个的输入。每个单步调用的可靠性也许做到了 95%，但串行链路的累积失败概率会远高于任何单步。对于关键业务链路，预定义"工具调用模板"——限定模型只能在已验证的调用模式中选择，而不是完全自由组合——是用灵活性换取确定性的务实选择。

### 阶段六：持续度量 —— 没有数据就没有可靠性

可靠性工作有一个反直觉的特点：**你做的优化越多，越难判断哪一步真正起了作用。** 因为 Function Calling 的失败是概率性的，不是每次都会重现。如果缺乏系统性的度量，你可能会花大量精力修一个"看起来重要"的问题，而忽略了那个"实际最高频"的失败模式。

**离线评估的核心是建立标准测试集。** 从真实用户请求中抽样，人工标注每个请求的"期望工具调用"和"期望参数"，构建一个 benchmark。每次修改 Schema、调整 Prompt 或升级模型版本，都跑全量回归，观察工具选择准确率、参数正确率、端到端任务完成率的变化方向。这和传统软件的单测、回归测试逻辑一致——只是被测对象从确定性代码变成了概率性模型。

**线上监控要盯住全链路的关键节点。** 至少要覆盖：调用触发率（验证意图识别是否准确）、参数校验通过率（衡量参数质量）、工具执行成功率（反映下游稳定性）、重试率和重试成功率（评估容错机制的有效性）、端到端任务完成率（用户视角的最终体验）。为每个指标设告警阈值，确保异常能在第一时间被感知。

对于一些规则难以覆盖的"软问题"——比如模型选了一个不算错但并非最优的工具，或者参数的语义有微妙偏差——可以采用 LLM-as-Judge 的方式做离线抽样评估，用一个独立的模型来评判调用决策的合理性。成本较高，不适合线上实时使用，但对持续优化方向的判断非常有价值。

## 技术总结

Function Calling 的可靠性，不是靠某个单点技术能"修好"的。它天然是一个要在概率系统外部叠加强确定性约束的工程问题，所以它的解法也天然是分层的：Schema 设计在语义层面收敛表达空间，Structured Output 在解码层面冻结格式边界，校验+重试+降级在工程层面提供执行兜底，而评估监控体系保证你始终在正确的方向上迭代。

还有一个在技术讨论中容易被忽略的维度：**投入与风险的关系**。一个内部使用的数据查询助手，出错了大不了让用户重新问一次，基础的校验和重试完全够用。但一个能发起支付、修改账户权限的 Agent，每次误操作都是真金白银。这时候，在关键操作前插入人工确认节点、对高风险工具施加更严格的参数校验、甚至引入双模型交叉验证——这些"过度工程"就有了充分的合理性。工程上的可靠性从来不是绝对值，而是在成本、延迟和安全之间找到与你业务风险匹配的平衡点。
